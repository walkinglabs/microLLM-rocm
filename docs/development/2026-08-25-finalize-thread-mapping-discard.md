# 为什么“少开一些线程”没有明显变快

## 一个容易误会的地方

DeepSeek每个Attention head有128列，旧Kernel开256个线程。在最后的加权求和阶段，线程0到127
各算一列，线程128到255看起来没有算列。很容易得出结论：把线程改成128，应该快一倍。

但是一个Kernel不只做这一件事。前面还要找最大分数、计算指数、把所有指数相加。原来的256个
线程各自负责一条固定序列：

```text
lane 0: position 0, 256, 512, ...
lane 1: position 1, 257, 513, ...
```

为了不改变浮点结果，新实现让128个物理线程分别模拟两条逻辑lane；64个线程则各模拟四条。
共享内存的加法树保持完全相同，所以结果可以位级一致。

## 我们实际测了什么

不是只测一个shape。矩阵包含Qwen和DeepSeek、长短上下文、batch 1/2、FP32/BF16缓存，三种线程
配置各启动两个新进程，总共96条记录。每条先检查完整context，再计时。

结果是128-thread最好也只快1.21%，有些case慢约1%；64-thread全部更慢。原因是最后那条
`position 0→T`累加链并没有缩短，value数据也没有少读。少线程只是把更多逻辑工作交给同一个
物理线程。

## 为什么还保留这个接口

它是一个明确的研究开关，不会被模型自动选择。以后换GPU、wave大小或编译器版本时，可以用同一
runner复测，而不用重新改Kernel。当前MI300X结论仍然是：不把128-thread写成默认。

下一实验会保持score和softmax的顺序，只把P×V拆成多个sequence片段。这样若精度失败，我们就
知道value累加顺序本身不能随意改变。
