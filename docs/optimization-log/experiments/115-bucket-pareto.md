# Experiment 115：两个 B4 桶是当前负载的折中点

## 为什么继续测

Experiment 114 只比较了两个端点：一个 B8 大池与四个 B2 小池。四桶省 52.91% KV，却损失
约 42% 吞吐。我们还不知道中间有没有更实用的点。

本轮只增加一个配方：

```text
一个桶：2064×8
两个桶：520×4 + 2064×4
四个桶：264×2 + 520×2 + 1040×2 + 2064×2
```

请求、总 slot、模型、精度、热身和重复次数完全不变。

## 先拒绝一轮受污染的“成功”

第一次 runner 输出 18/18 `status=pass`，但 GPU telemetry 在 DeepSeek 阶段突然出现 60% VRAM，
随后升到 96%；外部进程占用约 166 GB。DeepSeek 四桶吞吐也波动到 131–157 tokens/s。

这说明“程序成功退出”不是性能证据。该轮整体标记 `partial_invalid`，0 条性能行进入正式表。
随后 runner 增加物理 GPU pre/post idle gate。正式 18 条记录 pre VRAM 全为 0%，post 最大 2%。

## 两桶相对一个桶

两模型几乎得到同一个变化：

```text
KV backing          -37.40%
median TTFT          -34.5% 到 -34.8%
throughput           -13.7% 到 -13.9%
TTFT p95             +6.9% 到 +7.5%
completion p50       +19.0% 到 +20.0%
engine peak          只下降 3.1% 到 3.6%
```

18/18 正式进程通过，两个模型在 1/2/4 桶下的生成 token 都 exact。

## 结论

一个桶仍是吞吐和尾延迟默认。两个桶是当前固定长请求分布的 balanced opt-in：它用约 14% 吞吐
代价换 37.4% KV backing 和约 35% median TTFT 改善。四桶只适合 KV 极度紧张的显式场景。

这个结论不能自动推广到真实在线流量。当前请求刚好平均分布在各桶，且全部在开始时提交。下一
节点应加入偏斜长度分布和延迟到达，直接测没有 slot stealing 时的排队反例，再决定是否实现借用。

## 数值边界

本轮证明同一 microLLM 模型在三种 bucket policy 下 token exact；没有匹配 PyTorch 的可变位置
连续调度器，因此不把它写成跨框架 serving parity。
