# Step 11 — cached FP8 weights and dynamic activation scaling

Status: `planned`

## New track

FP8 has its own score and accuracy budget. It cannot be connected to the FP32/BF16 line.

## Hypothesis

FP8 becomes useful only when weights are prequantized/cached and activation scale
calculation does not erase GEMM gains.

## Design stages

1. cache E4M3FNUZ weight + scale;
2. refresh only after optimizer update;
3. dynamic activation amax;
4. amax history/delayed scaling;
5. E4M3/E5M2 policy;
6. BF16/FP32 accumulation boundaries;
7. optional FP8 KV cache only after FP32/BF16 cache is stable.

## Required tests

- saturation and zero ratios;
- dequantized tensor error;
- scaled GEMM error;
- full logits/loss/gradient;
- generated token stability;
- scale state checkpoint/resume;
- quantization cost inside end-to-end timing.

## Falsification

If prequantized GEMM improves but end-to-end does not, projections are no longer the
main bottleneck. Do not add more FP8 formats until the timeline supports them.

## Keep gate

Official-model end-to-end throughput or memory improves under an explicit accuracy
budget. Fixed manual scale alone is not a release-quality result.
